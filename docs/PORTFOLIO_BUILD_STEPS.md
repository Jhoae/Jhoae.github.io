# 오재호 백엔드 포트폴리오 실행 Step

> 목적: 포트폴리오 원칙을 실제 콘텐츠와 GitHub Pages 사이트로 옮기기 위한 실행 순서
>
> 대상: `Jhoae/Jhoae.github.io`
>
> 첫 번째 프로젝트: AIRS
>
> 기준일: 2026-07-29
>
> 원칙: 한 Step의 완료 조건을 만족한 뒤 다음 Step으로 이동한다.

---

## 0. 이 실행 계획의 핵심

포트폴리오는 다음 순서로 만든다.

```text
저장소 보존
→ 사실과 근거 수집
→ 지원자 포지셔닝
→ 사이트 구조 확정
→ 자기소개 작성
→ 핵심 역량 작성
→ AIRS 프로젝트 요약
→ 대표 문제 해결 사례 작성
→ 아키텍처와 코드 근거 연결
→ 문장·수치 검수
→ 정적 사이트 구현
→ 공개 전 최종 검증
→ GitHub Pages 배포
```

중요한 것은 사이트를 먼저 예쁘게 만드는 일이 아니다.

1. 먼저 사실을 확정한다.
2. 그 사실이 어떤 백엔드 역량을 보여주는지 정한다.
3. PAAR 구조로 문장을 작성한다.
4. 문장이 확정된 뒤 화면에 배치한다.

이 순서를 바꾸면 다음 문제가 생긴다.

- 빈 화면을 채우기 위해 기술 이름을 나열한다.
- 아직 측정하지 않은 성과를 만들게 된다.
- 같은 내용을 여러 메뉴에 반복한다.
- 디자인은 완성됐지만 면접에서 설명할 내용이 약해진다.
- AIRS 소개 사이트가 되고 오재호의 포트폴리오가 되지 못한다.

## 1. 전체 사이트 범위부터 단순하게 고정한다

### 1.1 목표

방문자가 한 페이지에서 다음 네 가지를 이해하게 한다.

1. 오재호가 누구인가.
2. 어떤 방식으로 백엔드 문제를 해결하는가.
3. AIRS에서 무엇을 직접 분석·구현·검증했는가.
4. 더 자세한 코드와 GitHub는 어디에서 볼 수 있는가.

### 1.2 최종 사이트 구조

상단 내비게이션은 다음 네 개만 사용한다.

```text
About | Competencies | AIRS | Contact
```

페이지 내부는 다음처럼 구성한다.

```text
Home
├─ Hero
├─ About
├─ Backend Competencies
├─ Project 01 — AIRS
│  ├─ Project Overview
│  ├─ Role and Contribution
│  ├─ Architecture
│  ├─ Problem Solving 01
│  ├─ Problem Solving 02
│  ├─ Problem Solving 03
│  ├─ Verification and Limitations
│  └─ Repository
└─ Contact
```

### 1.3 별도 최상위 섹션으로 만들지 않을 항목

#### Troubleshooting

Troubleshooting은 AIRS와 떨어져 존재하는 경력 항목이 아니다. AIRS 내부의 `Problem Solving` 사례로 포함한다.

이유:

- 문제가 어떤 프로젝트 맥락에서 발생했는지 바로 이해할 수 있다.
- 같은 아키텍처 설명을 반복하지 않는다.
- 기술 블로그 목록처럼 보이는 것을 피한다.

#### Engineering Principles

별도의 긴 선언문을 만들지 않는다.

다음 위치에 짧게 반영한다.

- About의 문제 해결 방식
- Competencies의 근거 문장
- AIRS 사례의 분석·검증·한계

“저는 테스트를 중요하게 생각합니다”라고 선언하는 것보다, 테스트 파일과 검증 과정으로 보여준다.

#### Technology Stack

기술 로고만 모은 독립 섹션은 만들지 않는다.

기술은 다음 위치에서 맥락과 함께 보여준다.

- Competencies: 어떤 문제에 사용했는지
- AIRS Overview: 프로젝트에서 실제 사용한 기술
- Problem Solving: 선택 이유와 트레이드오프

필요하면 AIRS 하단에 작은 텍스트 표를 둔다.

### 1.4 완료 조건

- [ ] 메뉴가 4개 이하인가?
- [ ] Troubleshooting이 AIRS 안에 포함됐는가?
- [ ] Engineering Principles가 별도 감성 에세이가 아닌가?
- [ ] 기술 스택보다 사람과 프로젝트가 먼저 보이는가?
- [ ] 한 페이지에서 전체 내용을 읽을 수 있는가?

## 2. 두 GitHub 저장소의 역할을 명확히 분리한다

### 2.1 `Jhoae/airs-backend`

역할:

- AIRS backend 최종 코드 보존
- 원본 `airs-release/backend`와의 출처 관계 유지
- 포트폴리오에서 코드 근거로 연결

원칙:

- GitHub의 공개 fork 기능을 사용한다.
- fork 설명에 AIRS backend 보존·포트폴리오 참고 목적을 명시한다.
- 원본 팀의 작업을 개인 단독 성과처럼 표현하지 않는다.
- 개인 기여는 별도 포트폴리오에서 클래스·커밋·문서 근거로 구분한다.
- 원본 repository의 license와 저작권 표시를 유지한다.
- 저장소 보존을 이유로 팀 기록을 임의 수정하지 않는다.

포트폴리오 링크 문구:

```text
AIRS backend source — forked from airs-release/backend
```

피해야 할 문구:

```text
My AIRS backend
오재호가 개발한 AIRS 전체 백엔드
개인 프로젝트 AIRS
```

팀 프로젝트였다면 팀 프로젝트라고 명시해야 한다.

### 2.2 `Jhoae/Jhoae.github.io`

역할:

- 오재호의 백엔드 포트폴리오 원본
- GitHub Pages 배포 source
- 포트폴리오 콘텐츠·스타일·근거 링크 관리

원칙:

- AIRS 코드를 복사하지 않는다.
- AIRS 코드 링크는 `Jhoae/airs-backend`로 연결한다.
- 포트폴리오 콘텐츠와 프로젝트 코드를 한 저장소에 섞지 않는다.
- 사이트는 정적이고 단순하게 유지한다.
- 공개 전 검증되지 않은 초안은 `docs/`에 두고 `index.html`에는 넣지 않는다.

### 2.3 저장소 공개 전 확인

- [ ] AIRS 원본이 공개 저장소인가?
- [ ] 공개하면 안 되는 secret이 Git history에 없는가?
- [ ] 원본 license를 확인했는가?
- [ ] 포트폴리오 repository에 운영 비밀 정보가 없는가?
- [ ] 두 저장소의 README가 역할을 혼동하지 않게 설명하는가?

### 2.4 완료 조건

- [ ] `Jhoae/airs-backend`가 원본과 fork 관계를 유지한다.
- [ ] `Jhoae/Jhoae.github.io`가 별도 공개 저장소로 존재한다.
- [ ] 각 repository의 설명이 목적을 명확히 나타낸다.
- [ ] 포트폴리오가 아직 미완성이라면 Pages 배포를 서두르지 않는다.

## 3. AIRS의 기준 시점을 동결한다

### 3.1 목표

프로젝트 종료 후 코드와 문서가 더 바뀌지 않는다는 전제로, 포트폴리오에서 설명할 기준 상태를 고정한다.

기록할 항목:

- 기준 repository
- 기준 branch
- 기준 commit SHA
- 확인 날짜
- 프로젝트 종료 상태
- Raspberry Pi 접근 가능 종료일
- 이후 추가 검증이 불가능한 범위

### 3.2 기준 기록 템플릿

```markdown
## AIRS Portfolio Baseline

- Source:
- Branch:
- Commit:
- Verified at:
- Project status: Ended
- Runtime access: Raspberry Pi access unavailable after 2026-08-06
- Evidence scope:
```

### 3.3 반드시 지킬 점

- 기준 commit 이후의 계획을 현재 구현으로 쓰지 않는다.
- 종료된 서비스를 현재 운영 중이라고 쓰지 않는다.
- Raspberry Pi에 계속 접근할 수 있는 것처럼 검증 계획을 만들지 않는다.
- 종료 전에 확보한 테스트·로그·문서만 실제 결과로 사용한다.
- 코드에는 있지만 실행하지 않은 기능은 `구현`으로만 표시한다.
- 실제로 실행한 항목만 `실측 검증`으로 표시한다.

### 3.4 피해야 할 표현

```text
현재 AIRS를 운영하고 있습니다.
지속적으로 사용자가 이용하고 있습니다.
추후 AIRS에 Kafka를 적용할 예정입니다.
운영 중 발생한 대규모 트래픽을 처리했습니다.
```

### 3.5 완료 조건

- [ ] 기준 commit을 기록했는가?
- [ ] 프로젝트 종료 상태가 명확한가?
- [ ] 현재 구현·실행 결과·향후 계획이 구분됐는가?
- [ ] 추가 검증이 불가능한 범위를 알고 있는가?

## 4. 글을 쓰기 전에 Evidence Ledger를 만든다

### 4.1 목표

포트폴리오에 쓸 문장을 먼저 만들지 않고, 사용할 수 있는 사실을 근거와 함께 모은다.

### 4.2 근거 유형

우선순위:

1. 현재 `main` 코드
2. 현재 코드로 수행한 실제 검증 결과
3. 테스트
4. 최신 실험 문서
5. 최신 설계 문서
6. 커밋
7. 오래된 문서
8. 향후 계획

문서와 코드가 충돌하면 현재 코드와 실제 결과를 우선한다.

### 4.3 Ledger 열

| ID | 후보 주장 | 상태 | 코드 | 테스트 | 로그·실험 | 한계 | 공개 여부 |
|---|---|---|---|---|---|---|---|

상태는 다음 중 하나만 사용한다.

- `구현 확인`
- `테스트 확인`
- `실측 검증`
- `문서만 확인`
- `향후 계획`
- `폐기`

### 4.4 AIRS에서 먼저 채울 항목

#### MQTT ingestion

- callback의 책임
- dispatcher의 worker 수
- queue 크기와 포화 정책
- nodeId worker 선택
- MySQL·InfluxDB 저장 흐름
- 중복·순서 guard
- Redis 장애 정책
- 초기 재현 수치
- 개선 후 검증 수치
- 미검증 항목

#### Time-series query

- raw 주기
- 기간별 adaptive window
- raw/rollup 선택 기준
- InfluxDB Task
- Redis cache key와 TTL
- 동일 miss lock
- leader/follower
- lock TTL 연장
- Redis fallback
- 내부 hit/miss metric

#### Data modeling

- MySQL이 보관하는 상태
- InfluxDB가 보관하는 raw
- rollup의 원본성
- raw 삭제 정책
- Flyway migration

#### Security and operations

- JWT 인증
- 역할별 인가
- 관리자 신청 상태
- Docker
- Caddy
- GitHub Actions
- smoke test

### 4.5 주장 하나를 승인하는 기준

다음 질문에 모두 답할 수 있어야 한다.

- 어디에 구현돼 있는가?
- 실제로 실행했는가?
- 무엇으로 확인했는가?
- 수치의 조건은 무엇인가?
- 내가 직접 설명할 수 있는가?
- 어디까지 일반화할 수 있는가?

한 항목이라도 답할 수 없으면 문장을 약하게 바꾸거나 공개하지 않는다.

### 4.6 완료 조건

- [ ] 모든 대표 수치에 출처가 있는가?
- [ ] 모든 기술에 실제 사용 위치가 있는가?
- [ ] 구현과 실측이 구분됐는가?
- [ ] 문서·코드 충돌이 표시됐는가?
- [ ] 미사용 기술이 제거됐는가?
- [ ] 각 주장에 한계가 있는가?

## 5. 오재호의 포지셔닝을 한 문장으로 정한다

### 5.1 목표

AIRS를 소개하기 전에, 오재호가 어떤 백엔드 개발자인지 한 문장으로 정한다.

### 5.2 문장 공식

```text
[검증 가능한 문제 또는 규모]에서
[직접 수행한 행동]으로
[지킨 품질]을 보여준
백엔드 개발자 오재호입니다.
```

### 5.3 사용할 수 있는 키워드

- 병목 재현
- 호출 흐름 추적
- 데이터 흐름 확인
- 정합성
- 순서 보존
- 중복 방지
- bounded resource
- 장애 fallback
- 실험과 검증
- 한계 기록

키워드는 최대 세 개만 한 문장에 사용한다.

### 5.4 작업용 후보

후보 A:

> 호출과 데이터 흐름을 근거로 병목을 찾고, 정합성·장애 fallback·검증 가능성을 함께 설계하는 백엔드 개발자 오재호입니다.

후보 B:

> 격리된 환경에서 문제를 재현하고, 순서·중복·메모리 한계를 함께 고려해 개선 결과를 검증하는 백엔드 개발자 오재호입니다.

후보 C:

> 기술 도입 자체보다 문제의 원인과 선택의 근거, 측정 가능한 결과를 설명하는 백엔드 개발자 오재호입니다.

최종 문장은 Evidence Ledger를 완성한 뒤 선택한다.

### 5.5 규모감을 넣는 규칙

규모를 넣을 수 있는 경우:

- 실제 값이 있다.
- 실행 환경을 말할 수 있다.
- 가상 대상과 물리 대상을 구분한다.
- 면접에서 측정 방법을 설명할 수 있다.

규모를 넣으면 안 되는 경우:

- “많았다”는 기억만 있다.
- 여러 실험의 숫자를 합친 값이다.
- 사용자 수를 추정했다.
- 실제 센서를 가상 node identity와 혼동한다.
- 짧은 실험을 운영 처리량으로 일반화한다.

### 5.6 피해야 할 자기소개

```text
끊임없이 성장하는 개발자입니다.
커뮤니케이션을 중요하게 생각합니다.
안정적이고 확장 가능한 서비스를 만듭니다.
대규모 트래픽 처리 경험이 있습니다.
다양한 기술을 경험한 백엔드 개발자입니다.
```

문제점:

- 누구에게나 적용된다.
- 검증 가능한 행동이 없다.
- 면접 질문으로 이어지지 않는다.
- 신입 경험을 과장할 위험이 있다.

### 5.7 완료 조건

- [ ] 한 문장만 읽어도 역할이 보이는가?
- [ ] 오재호의 행동이 있는가?
- [ ] 추상적인 성격 소개가 아닌가?
- [ ] 규모를 넣었다면 조건과 근거가 있는가?
- [ ] AIRS 하나에만 종속되지 않는가?

## 6. About은 경력 에세이가 아니라 작업 방식을 설명한다

### 6.1 목표

About은 개인 서사보다 백엔드 문제를 대하는 방식을 3~5문장으로 설명한다.

### 6.2 권장 구조

1. 어떤 문제를 중요하게 보는가.
2. 문제를 어떻게 확인하는가.
3. 선택할 때 무엇을 함께 고려하는가.
4. 구현 후 무엇으로 검증하는가.
5. AIRS가 이를 어떻게 보여주는가.

### 6.3 작업용 템플릿

```text
저는 문제가 발생한 계층을 먼저 추측하기보다 실제 호출과 데이터 흐름을 확인합니다.
운영 환경과 분리된 재현 환경에서 병목을 만들고, 처리량뿐 아니라 순서·중복·메모리 상한·장애 시 동작을 함께 살핍니다.

구현 후에는 테스트와 로그, 저장 결과를 통해 확인한 범위와 아직 증명하지 못한 범위를 함께 기록합니다.
```

위 문장은 최종 원고가 아니라 방향 예시다. AIRS 근거와 중복되는 문장은 줄인다.

## 9. 대표 Problem Solving 사례는 세 개부터 작성한다

### 9.1 목표

기술의 다양성보다 오재호의 분석과 선택을 깊게 보여주는 사례 세 개를 완성한다.

### 9.2 우선순위 후보

#### 사례 1 — MQTT 수집 병목

보여주는 역량:

- 문제 재현
- 호출 흐름 추적
- broker 로그 분석
- 동시성 설계
- 순서·메모리·backpressure
- 부하 검증

#### 사례 2 — 시계열 조회와 Redis cache

보여주는 역량:

- 데이터 특성 이해
- raw/rollup 선택
- cache stampede
- 분산 lock
- TTL 연장
- 장애 fallback
- metric 분리

#### 사례 3 — QoS 1 중복·순서 역전

보여주는 역량:

- 전달 보장과 멱등성
- 부팅 세션 식별
- Redis Lua
- 원자성
- fail-open tradeoff

네 번째 사례는 첫 세 사례가 완성된 뒤 필요할 때만 추가한다.

후보:

- MySQL/InfluxDB 데이터 모델링
- 인증·권한과 관리자 상태 전이
- Flyway·CI/CD·Raspberry Pi 배포
- CO2 변화량 알림 lifecycle

### 9.3 사례 선정 점수

각 항목 0~2점:

- 문제 중요도
- 본인 기여
- 원인 분석
- 대안 비교
- 코드 깊이
- 검증 수치
- 한계 설명
- 면접 확장성

점수가 낮은 사례는 억지로 채우지 않는다.

### 9.4 사례별 PAAR 작성

#### P — Problem

답할 질문:

- 기대값은 무엇이었는가?
- 실제 값은 무엇이었는가?
- 어떻게 발견했는가?
- 왜 중요한가?
- 어떤 조건에서 재현했는가?

피해야 할 시작:

```text
Redis를 사용하기 위해
성능을 개선하고 싶어서
대규모 트래픽에 대비하기 위해
새로운 기술을 공부하고 싶어서
```

좋은 시작:

```text
200개 가상 노드가 120초 동안 발행한 24,000건 중
InfluxDB에는 10,141건만 적재됐고 broker drop 로그가 남았다.
```

#### A — Analyze

답할 질문:

- 최초 가설은 무엇이었는가?
- 어느 클래스부터 확인했는가?
- 어떤 호출 흐름이 보였는가?
- 로그와 DB count가 무엇을 보여줬는가?
- 원인이 아니었던 것은 무엇인가?
- 대안은 무엇이었는가?
- 선택 기준은 무엇이었는가?

Analyze를 생략하면 기능 나열형 글이 된다.

#### A — Action

답할 질문:

- 어떤 책임을 분리했는가?
- 어떤 클래스가 새 책임을 갖는가?
- 데이터는 어떤 순서로 흐르는가?
- 동시성을 어떻게 제어하는가?
- 장애 시 어떻게 되는가?
- 어떤 비용을 감수했는가?
- 테스트는 무엇을 확인하는가?

기술 이름보다 동작을 먼저 설명한다.

```text

```

보다:

```text
동시 요청에서도 최대 sequence 비교와 갱신이 분리되지 않도록
두 동작을 Redis Lua 한 번으로 수행했다.
```

#### R — Result

답할 질문:

- 어디에서 실행했는가?
- 부하 조건은 무엇인가?
- 몇 건을 얼마나 오래 실행했는가?
- 성공 기준은 무엇인가?
- 정합성도 확인했는가?
- 오류 로그를 확인했는가?
- 무엇은 아직 증명하지 못했는가?

## 11. 모든 핵심 문장을 Before/After로 검수한다

### 11.1 `도입했습니다`

Before:

```text
Redis를 도입했습니다.
```

After:

```text
같은 시계열 요청의 InfluxDB 재집계를 줄이기 위해 전체 응답을 Redis에 저장했다.
동일 키의 동시 miss에서는 잠금을 획득한 요청만 원본을 조회하게 했다.
```

### 11.2 `개선했습니다`

Before:

```text
MQTT 처리 성능을 개선했습니다.
```

After:

```text
callback 내부의 MySQL·InfluxDB·재실 판정 직렬 처리를 분리하고,
nodeId 기반 worker로 노드별 순서를 보존했다.
```

### 11.3 `안정성을 확보했습니다`

Before:

```text
bounded queue로 안정성을 확보했습니다.
```

After:

```text
queue 크기를 제한해 지속 부하에서 메모리가 무제한 증가하지 않게 했다.
포화 시 메시지를 버리지 않고 enqueue가 대기하도록 했다.
```

### 11.4 `조회 속도를 크게 향상했습니다`

Before:

```text
Redis로 조회 속도를 크게 향상했습니다.
```

After:

```text
Spring 내부 계측에서 같은 temperature + 1mo 요청의
cache miss 평균은 43.61ms, hit 평균은 4.78ms였다.
```

측정 계층과 조건을 함께 설명한다.

### 11.5 `대규모 트래픽`

Before:

```text
대규모 IoT 트래픽을 처리했습니다.
```

After:

```text
개발 Mac의 격리된 Docker staging에서
1,000개 가상 node identity가 5초 주기로 만든
24,000건의 수집 경로를 검증했습니다.
```

### 11.6 금지 또는 제한 표현

근거 없이 사용하지 않는다.

- 대규모
- 안정적
- 견고한
- 확장 가능한
- 고가용성
- 최적화
- 성능을 크게 개선
- 효율 향상
- 비용 절감
- 가시성 확보
- 사용자 경험 향상
- 성공적으로
- 완벽하게
- 획기적으로
- 실무 수준
- 운영 수준

사용하려면 바로 뒤에 기준을 붙인다.

```text
안정적이었다
```

## 12. 수치와 실험 조건을 최종 확정한다

### 12.1 초안의 `N`

초안에서는 다음처럼 쓸 수 있다.

```text
처리량 N배 개선 [EVIDENCE_REQUIRED]
조회 N초 → Nms [EVIDENCE_REQUIRED]
오류 N건 → 0건 [EVIDENCE_REQUIRED]
```

하지만 공개 사이트에는 다음 중 하나로 바꾼다.

1. 검증된 실제 수치
2. 수치 없는 관찰 사실
3. 검증하지 못했다는 한계
4. 문장 삭제

`N`을 공개하지 않는다.

### 12.2 수치마다 기록할 조건

- 날짜
- branch/commit
- 실행 장비
- 운영/staging
- 물리/가상
- 요청 또는 발행 수
- 주기/RPS
- 실행 시간
- 동시성/연결 수
- 측정 위치
- 성공 기준
- 한계

### 12.3 초기와 개선 후 MQTT 실험

두 실험은 총 24,000건이라는 점은 같지만 조건이 다르다.

| 항목 | 초기 | 개선 후 |
|---|---:|---:|
| 가상 노드 | 200 | 1,000 |
| 노드별 주기 | 1초 | 5초 |
| 시간 | 120초 | 120초 |
| 총 발행 | 24,000 | 24,000 |
| Influx `co2_ppm` | 10,141 | 24,000 |

따라서 다음 문장을 쓰지 않는다.

```text
같은 조건에서 적재율을 42.25%에서 100%로 개선했다.
```

대신:

```text
초기 200개·1초 주기 실험에서 누락과 broker drop을 재현했다.
구조 개선 뒤에는 1,000개·5초 주기 버스트 조건으로
다시 24,000건을 발행해 전량 적재를 확인했다.
두 실험의 부하 패턴이 달라 개선율로 환산하지 않았다.
```

### 12.4 `0건` 작성법

나쁜 문장:

```text
오류 0건
중복 0건
```

좋은 문장:

```text
해당 120초 실행에서 Mosquitto dropped/error/denied 로그를 확인하지 못했다.
```

관찰 시간과 대상이 있어야 한다.

- lock이 만료되면 어떻게 되나요?
- follower는 얼마나 기다리나요?
- leader가 죽으면 어떻게 되나요?
- Redis 장애 시 왜 API를 실패시키지 않나요?
- stale response는 어떻게 다루나요?

#### Delivery guard

- QoS 1은 정확히 한 번 전달이 아닌가요?
- `boot_id`가 왜 필요한가요?
- sequence 비교와 저장을 왜 Lua로 하나요?
- Redis 장애 시 fail-open의 위험은 무엇인가요?

8. 팀 전체 성과를 개인 단독 성과로 쓰지 않는다.
9. 감성 문장보다 코드와 실험 근거를 우선한다.
10. 장식보다 읽기 흐름을 우선한다.
11. 프로젝트 수를 채우기 위해 약한 프로젝트를 추가하지 않는다.
12. 로컬 트러블슈팅 문서를 명시적 승인 없이 push하지 않는다.

이 기준을 지킨 상태에서 한 Step씩 진행한다.
