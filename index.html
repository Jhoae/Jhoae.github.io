Problem Solving

대표 문제 해결 사례

01

MQTT callback에서 저장 작업을 분리

가상 node 1,000개의 버스트 조건에서 발행·적재 24,000건과 노드별 24건을 확인했습니다.

문제
200개 가상 node가 1초마다 120초간 QoS 1로 24,000건을 발행했지만, InfluxDB에는 10,141건만 적재되고 broker drop이 남았습니다.
확인
InfluxDB 쓰기만 의심하지 않고 callback부터 저장까지 추적했습니다. callback이 순번 검사, 재실 판정, MySQL snapshot, InfluxDB 적재를 한 흐름에서 수행하고 있었습니다.
선택과 구현
thread 설정 확대, 무제한 queue, 공용 pool을 비교한 뒤 callback은 검증과 enqueue까지만 담당하게 했습니다. nodeId를 8개 단일 worker에 고정하고 각 queue를 2,000개로 제한해 노드별 순서와 메모리 상한을 함께 관리했습니다.
검증
개발 Mac의 격리된 Docker staging에서 가상 identity 1,000개, MQTT 연결 50개, 5초 주기, 120초 조건으로 24,000건 전량 적재와 broker drop/error 없음, node·space snapshot 각 1,000행을 확인했습니다.

Queue 포화 시 callback을 대기시키는 선택은 지연을 남기지만, 임의 drop과 무제한 메모리 증가를 피합니다. hash가 한 stripe에 집중되면 hot spot이 생길 수 있습니다.

02

downsampling과 raw scan 비용을 분리

raw를 원본으로 유지하면서 기간별 hourly·daily rollup을 조회하는 경로를 구성했습니다.

문제
5일·1개월 요청의 반환 point는 약 120개로 줄었지만, InfluxDB는 기간에 포함된 5초 raw 전체를 계속 읽어 집계했습니다.
확인
응답량을 줄이는 downsampling과 원본 scan 비용은 별개였습니다. cache는 반복 요청만 줄이고, raw retention을 줄이면 재분석과 rollup 재생성의 기준을 잃습니다.
선택과 구현
1일은 raw, 5일은 hourly, 1개월은 hourly를 6시간 단위로 count 가중 집계하고 6개월·1년은 daily rollup을 우선했습니다. coverage가 비면 부분 결과를 섞지 않고 전체 raw 경로로 되돌렸습니다.
검증
raw 17,279건의 mean·min·max·count와 daily rollup 값이 일치했습니다. 같은 API의 단일 cold 요청 전체 시간은 당시 Raspberry Pi host 내부에서 7.385초에서 0.224초로 측정됐습니다.

Rollup은 조회 비용을 줄이는 파생 데이터입니다. 집계가 없거나 실패하면 raw로 우회하고, raw 자체는 수정하거나 자동 삭제하지 않았습니다.

03

동일 cache miss를 한 번의 원본 조회로 제한

동시 요청 20건을 InfluxDB load 1건으로 수렴시키고 나머지는 결과를 공유했습니다.

문제
같은 node·metric·period의 cache가 만료되는 순간 요청이 몰리면 모든 요청이 동일한 raw 또는 rollup을 다시 읽을 수 있었습니다.
확인
일반 cache hit만으로는 만료 시점의 중복 조회를 막지 못했습니다. JVM 내부 lock도 여러 Spring 인스턴스가 같은 cache를 사용할 때 요청을 조정할 수 없습니다.
선택과 구현
SET NX EX로 leader만 원본을 읽게 하고, token을 확인하는 Lua로 잠금 연장과 해제를 원자화했습니다. follower는 결과를 기다리거나 stale 응답을 사용하며, Redis 장애는 InfluxDB 직접 조회로 우회합니다.
검증
응답 key 하나만 삭제하고 동시 요청 20건을 보낸 결과 miss 1, hit_after_wait 6, hit 13과 InfluxDB hourly rollup load 1건을 확인했습니다.

센서 그래프에서는 수 초의 절대 최신성보다 조회 경로 유지가 낫다고 판단해 짧은 stale 허용 시간을 두었습니다.

04

QoS 1 중복과 순서 역전을 저장 전에 차단

노드의 부팅 세션과 순번을 함께 비교해 과거 telemetry가 최신 상태를 되돌리지 않게 했습니다.

문제
QoS 1 재전송이나 늦게 도착한 과거 메시지를 그대로 처리하면 InfluxDB 이력이 중복되고 MySQL 최신 snapshot과 재실 상태가 과거 값으로 바뀔 수 있었습니다.
확인
sequence_no만 비교하면 장치 재부팅 후 0부터 시작한 정상 메시지를 막습니다. Redis 값을 읽고 애플리케이션에서 비교한 뒤 쓰는 방식은 동시 요청 사이의 원자성도 보장하지 못합니다.
선택과 구현
boot_id + sequence_no를 키와 비교 기준으로 정하고, Redis Lua 한 번으로 최대 순번을 비교·갱신했습니다. duplicate와 out-of-order는 재실 계산과 MySQL·InfluxDB 저장 전에 중단합니다.
검증
단위 테스트에서 최초·증가 순번, 같은·작은 순번, 구형 payload, Redis 실패 경로를 확인했습니다. ingestion 테스트에서는 차단 뒤 snapshot과 raw writer가 호출되지 않는 경계를 검증했습니다.

Redis 장애 시 수집을 멈추지 않는 fail-open을 택했기 때문에, 해당 구간에는 중복 방어가 약해지는 비용이 남습니다.
