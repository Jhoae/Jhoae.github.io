System Design

  2. 02노드별 분배같은 nodeId를 항상 같은 single-thread worker로 보내 노드별 처리 순서를 유지합니다.
  3. 03순서 판정node별 MySQL 상태 행의 row lock을 획득한 뒤 boot_id·sequence_no로 중복·역전을 판정합니다.
  4. 04재실 상태 계산이전 PIR·마지막 움직임 상태와 현재 PIR·mmWave 입력으로 재실 결과를 계산합니다.
  5. 05상태·outbox 확정현재 telemetry로 node별 ingestion state와 최신 snapshot을 갱신하고, event별 InfluxDB outbox를 INSERT해 하나의 MySQL 트랜잭션에서 확정합니다.
  6. 06ACK·이력 전달MySQL commit 뒤 MQTT ACK를 완료하고, outbox publisher가 확정된 데이터를 InfluxDB에 전달합니다.

01

MQTT 수신과 저장 작업 분리

메시지 수신이 데이터베이스 저장을 기다리지 않도록 처리 흐름을 나눴습니다.

문제
MQTT telemetry가 짧은 시간에 몰렸을 때, 발행한 24,000건 중 10,141건만 InfluxDB에 저장됐고 Mosquitto 로그에도 Spring subscriber로 보내던 메시지의 drop이 남았습니다. 이 상태에서는 시계열 이력뿐 아니라 최신 상태와 재실 판정도 함께 누락될 수 있었습니다.
원인
MQTT 메시지가 도착할 때 자동으로 실행되는 Spring 수신 함수가 순번 확인, 재실 판정, MySQL 갱신, InfluxDB 저장까지 한 흐름에서 처리하고 있었습니다. 저장 작업이 길어질수록 이 수신 함수가 다음 메시지를 받지 못하는 구조였습니다.
해결

MQTT 메시지가 도착하면 Spring 수신 함수는 payload를 검증해 nodeId에 해당하는 queue로 넘기고, 실제 처리는 8개 single-thread worker가 맡도록 분리했습니다. 같은 node의 순서는 유지하면서 서로 다른 stripe는 병렬로 처리하고, node별 순번·재실 상태와 최신 snapshot, InfluxDB 전달용 outbox를 MySQL 트랜잭션에서 먼저 확정합니다. commit된 outbox 작업은 별도 publisher가 InfluxDB로 전달하도록 나눠, 상태 확정과 시계열 이력 전달의 책임을 분리했습니다.

선택한 이유
고정된 8개 thread로 같은 node의 순서와 node 간 병렬 처리를 함께 유지
수용한 비용
같은 stripe에 여러 node가 배정되면 서로의 처리를 기다립니다. queue가 가득 차면 MQTT 메시지가 도착할 때 실행되는 Spring 수신 함수도 빈자리를 기다리므로, broker의 미처리 메시지가 늘고 이후 메시지 수신이 늦어질 수 있습니다.
결과
노드 1,000개와 MQTT 연결 50개가 5초 주기·QoS 1로 120초간 발행한 24,000건을 모두 저장했습니다. 각 노드도 24건씩 일치했고 Mosquitto drop/error는 발생하지 않았습니다.
02

장기 시계열 조회에 rollup 적용

긴 기간의 시계열 조회가 5초 raw 전체를 매번 집계하지 않도록 조회 경로를 나눴습니다.

문제
활성 노드에서 수집한 CO₂ 값을 시간 구간별로 평균 내 그래프로 만들 때, 조회 기간에 포함된 5초 raw 데이터를 모두 읽어 집계해야 했습니다. 조회 기간이 길어질수록 첫 요청이 읽고 계산할 데이터가 늘었습니다.
원인
MQTT로 수집한 센서 값을 5초 raw point로만 저장한 상태에서는 API가 그래프의 시간대별 평균을 요청할 때마다 긴 기간의 원본을 다시 읽어야 했습니다. 캐시 역시 반복 요청은 줄일 수 있지만 캐시가 비어 있는 첫 조회의 비용은 해결하지 못했습니다.
해결
InfluxDB Task로 완료된 1시간·1일 구간의 raw 데이터를 주기적으로 평균·최솟값·최댓값·건수 rollup으로 미리 계산해 별도 bucket에 저장했습니다. 1일은 raw, 5일·1개월은 hourly, 6개월·1년은 daily rollup을 우선 조회하도록 경로를 나눴습니다. 집계 task와 파생 데이터를 추가로 관리해야 하지만, 필요한 rollup 데이터가 없으면 raw 데이터를 조회하도록 구성해 장기 조회의 원본 읽기 범위부터 줄였습니다.
결과
raw 17,279건의 평균·최솟값·최댓값·건수와 rollup 결과가 일치했습니다. 같은 CO₂ 분석 API의 캐시가 비어 있는 요청은 약 7초 → 0.2초로 줄었습니다.
03

캐시 만료 순간의 중복 원본 조회 제한

캐시가 비어 있는 동일 시계열 요청이 몰리면 한 요청을 leader로 정해 InfluxDB를 조회하고, 나머지는 결과를 재사용하는 1 leader·N follower 구조로 구현했습니다.

문제
같은 노드·지표·기간의 캐시가 만료되는 순간 요청이 몰리면 모든 요청이 동일한 raw 또는 rollup을 다시 조회할 수 있었습니다. 트래픽이 집중되는 시점에 InfluxDB 조회도 함께 늘어나는 구조였습니다.
원인
일반적인 캐시는 이미 저장된 응답만 재사용하기 때문에 여러 요청이 동시에 캐시 미스를 만나는 상황은 조정하지 못했습니다. 애플리케이션 내부 lock만 사용하면 여러 인스턴스가 같은 Redis 캐시를 사용할 때 서로의 조회 상태도 알 수 없었습니다.
해결
Redis 잠금을 먼저 얻은 요청을 leader로 정해 InfluxDB를 조회하고 새 응답을 저장했습니다. 응답은 최신 캐시로 30초간 사용하고, 그 뒤에도 마지막 성공 응답을 60초 더 보관했습니다. 이 응답이 남아 있으면 follower는 leader의 느린 조회가 끝날 때까지 기다리지 않고 기존 응답을 즉시 반환합니다. 반대로 캐시가 완전히 비어 이전 응답조차 없다면 follower가 재사용할 값이 없으므로 최대 1초 동안 leader가 저장할 결과를 기다립니다. Redis 장애나 대기 시간 초과에서는 API를 막지 않고 InfluxDB를 직접 조회하도록 했습니다.
결과
같은 캐시 키를 비운 뒤 20~500개의 동시 요청을 보낸 각 실험에서 Spring의 원본 조회 함수는 한 번만 실행됐고, 대기 시간 초과로 InfluxDB를 추가 조회한 요청도 없었습니다. 다만 500개 동시 요청에서는 요청의 95%가 완료되는 시간이 약 1.1초까지 늘었습니다. 캐시가 채워진 동일 조회는 30초 동안 30,002건을 처리했으며, 실패하거나 실행되지 못한 요청은 없었습니다.
04

중복·순서 역전 telemetry를 MySQL transaction에서 차단

중복·순서 판정과 실제 저장의 원자성을 위해, 장치의 부팅 세션·순번과 최신 상태·outbox를 하나의 MySQL 트랜잭션에서 확정했습니다.

문제
QoS 1 (최소 한 번 전달) 재전송이나 늦게 도착한 메시지를 그대로 처리하면 InfluxDB에 같은 이력이 중복 저장될 수 있었습니다. MySQL의 최신 상태와 재실 판정도 과거 데이터로 바뀔 수 있었습니다.
원인
sequence_no는 한 번의 부팅 세션 안에서만 증가하고 장치 재부팅 뒤에는 0부터 다시 시작합니다. 그래서 기존 구현은 node와 boot_id별 최대 sequence_no를 Redis에서 비교·갱신했습니다. 하지만 이 Redis 갱신이 MySQL·InfluxDB 저장보다 먼저 완료돼, Redis만 성공하고 DB 저장이 실패하면 같은 메시지의 재전송을 이미 처리한 중복으로 차단하는 문제가 발생했습니다.
해결
node별 telemetry_ingestion_states 행을 row lock으로 읽고 boot_id·sequence_no를 비교했습니다. 이 테이블에는 마지막으로 반영한 순번과 재실 계산 상태를, snapshot 테이블에는 API가 읽을 최신 상태를, telemetry_outbox에는 InfluxDB로 보낼 이력 작업을 저장했습니다. 최초·새 부팅 세션·증가 순번만 세 저장을 같은 MySQL 트랜잭션에서 확정하고, 같은·작은 순번은 모두 변경하지 않았습니다. outbox 재시도는 snapshot을 다시 갱신하지 않도록 책임을 분리했습니다.
결과
통합 테스트에서 최초·증가 순번만 반영되고 같은·작은 순번은 snapshot·재실 상태·outbox를 변경하지 않는 것을 확인했습니다. 40 → 42 → 41 순서에서도 41이 최신 상태를 덮지 않았습니다. boot_id나 sequence_no가 없는 구형 payload는 센서값 저장은 유지하되 중복·순서 차단 보장은 적용하지 않았습니다.
05

MQTT ACK와 저장 사이의 유실 경계 보완

MySQL에 최신 상태와 InfluxDB 전달 작업을 먼저 확정한 뒤 broker에 ACK하고, 실패한 이력 전달은 outbox에서 이어서 처리했습니다.

문제
MQTT 메시지를 받은 Spring은 메모리 queue에 저장 작업을 넘긴 뒤 broker에 수신 완료를 알리고 있었습니다. 이 사이에 Spring이 종료되면 broker는 전달이 끝난 것으로 판단하지만, 아직 MySQL·InfluxDB에 저장되지 않은 telemetry를 재시작 후 복구할 근거가 없었습니다. QoS 1 조건으로 이전 코드를 실행해 DB 저장 전에 종료했을 때도, ACK된 메시지가 다시 처리되지 않는 것을 확인했습니다.
원인
MQTT ACK는 broker에게 메시지 전달이 끝났다고 알리는 신호인데, 기존에는 실제 저장 결과가 아니라 Spring 수신 함수의 반환을 기준으로 전송됐습니다. Redis의 순번도 DB 저장 전에 갱신됐고, 비동기 InfluxDB 저장은 작업을 메모리 buffer에 넘긴 시점에 호출이 끝나 실제 적재 성공과 재시작 후 미처리 작업을 확인할 수 없었습니다.
해결

메모리에서만 재시도하면 Spring이 재시작될 때 작업이 사라지고, telemetry 전체를 다시 처리하면 과거 메시지가 최신 snapshot과 재실 상태를 다시 계산할 위험이 있었습니다. 그래서 node별 순번·재실 상태, 최신 snapshot과 InfluxDB 전달용 outbox를 하나의 MySQL 트랜잭션에서 확정한 뒤 ACK하도록 변경했습니다.

outbox는 수락한 telemetry마다 InfluxDB에 보낼 데이터와 전달 상태를 보관하는 MySQL 테이블입니다. Spring의 별도 전달 작업은 저장되지 않은 이력만 다시 보내며 snapshot과 재실 상태는 다시 계산하지 않습니다. 두 DB의 반영 시점이 잠시 달라지고 telemetry마다 MySQL 저장과 완료 데이터 정리 비용이 추가되지만, 재시작 복구와 최신 상태 역전을 함께 막는 쪽을 선택했습니다.

결과

QoS 1 조건에서 MySQL 저장을 마친 뒤 ACK하기 전에 Spring을 종료하자 broker가 같은 메시지를 다시 전달했고, 이미 반영된 최신 상태와 outbox는 중복 저장되지 않았습니다. InfluxDB를 중단했을 때도 미전달 작업이 MySQL에 남아 Spring과 InfluxDB를 재시작한 뒤 처리를 완료했습니다. 노드 1,000개가 발행한 24,000건이 outbox와 InfluxDB에 모두 반영됐고, 순번 누락·영구 실패와 미처리 작업이 정리 과정에서 삭제되는 문제는 발생하지 않았습니다.

(1) 기존 ACK 선행 구조

                        └→ stripe worker

변경 후

Backend Engineering

백엔드 품질을 연결한 작업

데이터 저장 경계

MySQL은 관계형 데이터와 최신 snapshot, node별 수집 상태·InfluxDB outbox를 관리합니다. InfluxDB는 raw telemetry와 rollup, Redis는 시계열 응답 cache와 동일 cold miss의 single-flight lock을 맡겼습니다.

인증과 인가

JWT로 사용자를 식별하고, 실제 접근은 DB의 ROOT_ADMIN·ADMIN·USER 역할, 관리자 승인 상태와 캠퍼스 범위를 요청마다 확인했습니다.

스키마와 배포

Spring Boot를 멀티스테이지 Dockerfile로 이미지화하고, Raspberry Pi에서 MySQL·InfluxDB·Redis·Mosquitto·Caddy와 Docker Compose로 실행했습니다. GitHub Actions는 테스트 통과 후 배포 서버에서 Spring 이미지를 다시 빌드하고 health check로 기동을 확인합니다.
