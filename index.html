System Design

아키텍처와 데이터베이스 설계

  1. 01수신·변환topic에서 nodeId를 분리하고 JSON payload를 검증해 DTO로 변환합니다.
  2. 02노드별 분배같은 nodeId를 항상 같은 single-thread worker로 보내 노드별 처리 순서를 유지합니다.
  3. 03순서 판정node별 MySQL 상태 행의 row lock을 획득한 뒤 boot_id·sequence_no로 중복·역전을 판정합니다.
  4. 04상태 계산이전 PIR·마지막 움직임 상태와 현재 PIR·mmWave 입력으로 재실 결과를 계산합니다.
  5. 05상태·outbox 확정sequence·재실 상태·최신 snapshot과 InfluxDB 전달용 outbox를 하나의 MySQL 트랜잭션으로 확정합니다.
  6. 06ACK·이력 전달MySQL commit 뒤 MQTT ACK를 완료하고, outbox publisher가 확정된 데이터를 InfluxDB에 전달합니다.

Troubleshooting

대표 문제 해결 사례

01

MQTT 수신과 저장 작업 분리

메시지 수신이 데이터베이스 저장을 기다리지 않도록 처리 흐름을 나눴습니다.

선택한 이유
고정된 8개 single-thread worker로 같은 node의 순서를 유지하고, 서로 다른 stripe는 병렬로 처리
수용한 비용
같은 stripe에 배정된 node가 함께 기다리는 hot spot과 queue 포화 시 broker 방향으로 전파되는 수신 지연
문제
센서 메시지가 짧은 시간에 몰리자 발행한 24,000건 중 10,141건만 InfluxDB에 저장됐고, Mosquitto에도 메시지 drop이 남았습니다. 이 상태에서는 시계열 이력뿐 아니라 최신 상태와 재실 판정도 함께 누락될 수 있었습니다.
원인
MQTT callback이 메시지를 받은 뒤 순번 확인, 재실 판정, MySQL 갱신, InfluxDB 저장까지 한 흐름에서 처리하고 있었습니다. 저장 작업이 길어질수록 callback이 다음 메시지를 받지 못하는 구조였습니다.
해결
callback은 메시지를 queue에 넘기고 실제 저장은 nodeId 기준 8개 worker가 처리하도록 분리했습니다. 같은 node의 처리 순서를 유지하면서 node 수만큼 thread를 만들지 않기 위해 striped worker를 선택했고, queue 크기도 제한했습니다. queue가 가득 차면 데이터를 버리지 않고 수신 속도를 늦추며, 같은 stripe에 여러 node가 몰릴 때 생기는 대기는 수용했습니다.
결과
개발 Mac의 Docker staging에서 가상 노드 1,000개와 MQTT 연결 50개가 5초 주기·QoS 1로 120초간 발행한 24,000건을 모두 저장했습니다. 각 노드도 24건씩 일치했고 Mosquitto drop/error는 발생하지 않았습니다.
02

장기 시계열 조회에 rollup 적용

긴 기간의 시계열 조회가 5초 raw 전체를 매번 집계하지 않도록 조회 경로를 나눴습니다.

문제
5일·1개월 조회의 응답 point는 약 120개로 줄였지만, InfluxDB는 요청 기간에 포함된 5초 raw 데이터를 계속 읽고 있었습니다. 조회 기간이 길어질수록 첫 요청의 집계 비용이 커졌습니다.
원인
downsampling은 raw 데이터를 읽은 뒤 반환할 point를 줄이는 방식이어서 InfluxDB가 읽는 데이터의 양은 달라지지 않았습니다. 캐시 역시 반복 요청은 줄일 수 있지만 캐시가 비어 있는 첫 조회의 비용은 해결하지 못했습니다.
해결
응답 cache는 반복 요청에는 유효하지만 처음 실행되는 cold 조회의 raw scan을 줄이지 못했습니다. 그래서 1일은 raw, 5일·1개월은 hourly, 6개월·1년은 daily rollup을 우선하도록 조회 경로를 나눴습니다. 집계 task와 파생 데이터를 추가로 관리해야 하지만, 필요한 rollup이 없으면 raw로 돌아가도록 구성해 장기 조회의 원본 읽기 범위부터 줄였습니다.
결과
raw 17,279건의 평균·최솟값·최댓값·건수와 rollup 결과가 일치했습니다. 같은 CO₂ 분석 API의 단일 cold 요청은 당시 Raspberry Pi 내부 측정에서 7.385초 → 0.224초로 줄었습니다.
03

캐시 만료 순간의 중복 원본 조회 제한

같은 시계열 요청이 몰려도 먼저 들어온 한 요청만 원본을 조회하도록 했습니다.

문제
같은 노드·지표·기간의 캐시가 만료되는 순간 요청이 몰리면 모든 요청이 동일한 raw 또는 rollup을 다시 조회할 수 있었습니다. 트래픽이 집중되는 시점에 InfluxDB 조회도 함께 늘어나는 구조였습니다.
원인
일반적인 캐시는 이미 저장된 응답만 재사용하기 때문에 여러 요청이 동시에 캐시 미스를 만나는 상황은 조정하지 못했습니다. 애플리케이션 내부 lock만 사용하면 여러 인스턴스가 같은 Redis 캐시를 사용할 때 서로의 조회 상태도 알 수 없었습니다.
해결
Redis 잠금을 먼저 얻은 요청만 원본을 조회하고, 나머지 요청은 먼저 만들어진 캐시를 기다려 사용하도록 했습니다. 잠금은 소유자를 확인한 뒤 연장·해제하고, 이전 응답이 남아 있으면 갱신 중에도 재사용합니다. Redis에 문제가 생기면 API 요청은 InfluxDB 직접 조회로 이어지도록 했습니다.
결과
같은 캐시 키를 비운 뒤 20~500 VU로 요청했을 때 Spring의 원본 loader는 각 실행에서 한 번만 호출됐고 fallback은 없었지만, 500 VU의 P95는 약 1.1초까지 늘었습니다. 캐시가 채워진 동일 조회는 Mac staging의 Caddy 경로에서 30초 동안 실제 994.682 RPS로 처리했으며, 30,002건에서 실패와 dropped iteration은 없었습니다.
04

중복·순서 역전 telemetry를 MySQL transaction에서 차단

장치의 부팅 세션과 순번을 최신 상태 저장과 같은 트랜잭션에서 판정했습니다.

문제
QoS 1 재전송이나 늦게 도착한 메시지를 그대로 처리하면 InfluxDB에 같은 이력이 중복 저장될 수 있었습니다. MySQL의 최신 상태와 재실 판정도 과거 데이터로 바뀔 수 있었습니다.
원인
sequence_no만 비교하면 장치가 재부팅된 뒤 0부터 시작하는 정상 메시지도 과거 데이터로 판단하게 됩니다. 기존 Redis 상태는 실제 DB 저장보다 먼저 갱신돼, 저장이 실패해도 재전송 메시지를 이미 처리한 것으로 판단할 수 있었습니다.
해결
node별 MySQL 상태 행을 row lock으로 읽고 boot_id·sequence_no를 비교했습니다. 증가 순번만 재실 상태·snapshot·outbox와 같은 트랜잭션에서 반영하고, 동일하거나 작은 순번은 상태를 변경하지 않았습니다. outbox 재시도는 snapshot을 다시 갱신하지 않도록 책임을 분리했습니다.
결과
통합 테스트에서 최초·증가 순번만 반영되고 같은·작은 순번은 snapshot·재실 상태·outbox를 변경하지 않는 것을 확인했습니다. 40 → 42 → 41 순서에서도 41이 최신 상태를 덮지 않았고, 순번 정보가 없는 기존 payload는 호환 범위를 분리해 계속 처리했습니다.
05

MQTT ACK와 저장 사이의 유실 경계 보완

DB commit 뒤 ACK하고, InfluxDB 미전달 작업은 MySQL outbox에서 이어서 처리했습니다.

문제
코드 흐름을 점검하며 MQTT callback이 메모리 queue에 작업을 넘긴 뒤 반환하면, DB 저장 전에 프로세스가 종료될 때 메시지가 사라질 수 있는 경계를 발견했습니다. 기준 코드를 격리 staging에서 실행했을 때도 ACK 뒤 저장되지 않은 메시지가 재시작 후 복구되지 않았습니다.
원인
MQTT ACK, MySQL snapshot과 InfluxDB 적재의 완료 시점이 서로 달랐습니다. 특히 Redis 순번은 저장보다 먼저 바뀌었고, 비동기 InfluxDB write는 호출이 반환돼도 실제 적재 성공을 확인하거나 재시작 뒤 이어갈 상태가 없었습니다.
해결
in-memory retry는 Spring이 재시작되면 작업이 사라지고, 전체 telemetry를 다시 처리하는 방식은 과거 event가 최신 snapshot과 재실 상태를 다시 계산할 위험이 있었습니다. 그래서 순번·재실 상태·snapshot·outbox를 같은 MySQL 트랜잭션에서 한 번만 확정한 뒤 ACK하고, background publisher는 InfluxDB 전달만 재시도하도록 분리했습니다. event별 MySQL write와 cleanup 비용은 추가되지만, 재시작 복구와 최신 상태 역전 방지를 함께 만족하는 쪽을 선택했습니다.
결과
QoS 1 격리 staging에서 commit 뒤 ACK 전 종료된 메시지의 재전달과, InfluxDB 장애 중 RETRY로 남은 작업이 Spring 재시작 뒤 완료되는 흐름을 확인했습니다. 가상 node 1,000개가 발행한 24,000건이 outbox와 InfluxDB에 모두 반영됐고 sequence gap·DEAD·cleanup 오삭제는 없었으며, 서버 수신부터 outbox 완료까지 P95는 612.114ms였습니다.

Backend Engineering

백엔드 품질을 연결한 작업

데이터 저장 경계

MySQL은 관계형 데이터와 최신 snapshot, node별 수집 상태·InfluxDB outbox를 관리합니다. InfluxDB는 raw telemetry와 rollup, Redis는 시계열 응답 cache와 동일 cold miss의 single-flight lock을 맡겼습니다.

인증과 인가

JWT로 사용자를 식별하고, 실제 접근은 DB의 ROOT_ADMIN·ADMIN·USER 역할, 관리자 승인 상태와 캠퍼스 범위를 요청마다 확인했습니다.

스키마와 배포

Flyway migration을 MySQL Testcontainers로 검증하고, GitHub Actions 테스트·Docker Compose 기동·health check·Caddy HTTPS를 배포 흐름으로 연결했습니다.

배포 경로 확인

Raspberry Pi의 공개 HTTPS 경로에서 인증·인가를 포함한 혼합 읽기 요청을 30분간 실행했습니다. 총 9,001건에서 실패와 dropped iteration은 없었고 P95는 314.64ms였습니다.
